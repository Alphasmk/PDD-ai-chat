# Research: роли, блокировка и инициализация

## 1. Текущая авторизация

**Decision**: Сохранить JWT как подтверждение личности, проверять текущие role/is_blocked в БД при каждом защищённом обращении, входе и refresh. Не добавлять авторитетную роль в JWT и не кэшировать разрешения.
**Rationale**: `source/application/use_cases/user_use_cases.py` уже читает аккаунт в GetCurrentUserFromToken, LoginUser, ResetTokens и require_user. Это позволяет менять доступ при следующем обращении без массового отзыва токенов. Неверный пароль остаётся 401; блокировка сообщается только после проверки корректного пароля. Восстановление пароля лишь публикует сообщение и не меняет аккаунт.
**Alternatives considered**: Роль в JWT устаревает; массовая запись всех токенов в blacklist требует нового учёта сеансов и не нужна для текущей задачи.

## 2. Транзакции изменений

**Decision**: Добавить типизированный порт UoW для административных изменений и удаления собственного аккаунта. Сценарий завершает commit до возврата результата. Репозиторий в UoW выполняет SELECT FOR UPDATE с принудительным обновлением identity map для цели и узкие изменения соответствующих полей. Инициатор проверяется до чтения цели.
**Rationale**: Текущий session.py коммитит после yield. Подтверждение должно означать завершённый commit. `get_by_id` использует AsyncSession.get: повторное чтение внутри сессии может вернуть старое состояние. Общий update сейчас обновляет только профиль; это разделение надо сохранить. Fake-репозиторий сейчас заменяет сущность целиком, его поведение необходимо согласовать.
**Alternatives considered**: Проверка перед UPDATE без блокировки оставляет гонку назначения и блокировки; замена всей сущности может затереть новые права. Полная сериализация всех чтений избыточна: спецификация допускает завершение ранее начатых обращений.

Решение о строковых блокировках основано на [PostgreSQL 16: Explicit Locking](https://www.postgresql.org/docs/16/explicit-locking.html): конфликтующие изменения строки ожидают освобождения блокировки; транзакционные advisory locks освобождаются при завершении транзакции. Применение этих механизмов к bootstrap и ролям является проектным решением.

## 3. Каталог двух ролей и единственный суперадмин

**Decision**: Отдельные RoleEntity/ORM Role и таблица roles с двумя фиксированными записями user/admin. Users.role_id — внешний ключ; is_superadmin — защищённый статус администратора. Частичный уникальный индекс по is_superadmin WHERE is_superadmin обеспечивает максимум одного; startup обеспечивает наличие.
**Rationale**: Последнее требование явно задаёт отдельную таблицу и две роли; пользователь подтвердил сохранение защищённого суперадмина. Список читается из БД через IRoleRepository. FK и CHECK защищают модель; профиль не меняет полномочия.
**Superseded decision**: Первоначальный строковый enum user/admin/superadmin соответствовал предыдущему уточнению. Его заменяет forward-миграция с сохранением аккаунтов; редактируемый каталог через API не нужен.

## 4. Параллельный старт

**Decision**: Заменить последовательность shell «alembic upgrade head» на типизированный Python startup runner: взять session advisory lock на отдельном выделенном соединении PostgreSQL, применить Alembic через уже поддерживаемый config.attributes['connection'], затем bootstrap и commit, отпустить lock, только затем exec приложения. Блокировка охватывает миграции и bootstrap; соединение закрывается при ошибке. Все контейнеры используют один документированный ключ блокировки 74004001 в одной БД. Ожидание ограничить 60 секундами, timeout завершает старт ненулевым кодом с безопасной диагностикой.
**Rationale**: Блокировка только INSERT не устраняет гонку двух Alembic на новой БД. Advisory session lock переживает отдельные транзакции миграции и bootstrap. env.py уже поддерживает переданное Connection.
**Alternatives considered**: Независимый bootstrap после несериализованных миграций не гарантирует параллельный первый запуск; отдельный оркестратор миграций усложняет текущий контейнерный контракт.

## 5. Начальные данные

**Decision**: SUPERADMIN_USERNAME, SUPERADMIN_EMAIL, SUPERADMIN_PASSWORD, SUPERADMIN_NAME, SUPERADMIN_SURNAME обязательны только когда суперадмина ещё нет; телефон не задаётся. Пароль проходит существующий RawPassword и hasher, в настройках скрывается SecretStr. Читать и валидировать bootstrap-параметры после проверки существующего суперадмина, не делать их обязательными для импорта обычных настроек или тестов.
**Rationale**: Повторный запуск не должен менять профиль, требовать старые секреты или ломаться из-за изменённых начальных настроек. При наличии суперадмина выдавать безопасное информационное сообщение «начальные данные не применяются» без сравнения/логирования пароля. При конфликте username/email с обычным аккаунтом — отказ, не повышение.
**Alternatives considered**: Автоматический первый зарегистрировавшийся админ опасен; hardcoded пароль запрещён; повторная синхронизация профиля противоречит спецификации.

## 6. Пагинация и переход

**Decision**: limit=50 (1..100), offset=0 (>=0), сортировка created_at ASC, id ASC, ответ items/limit/offset; total не нужен. Итоговая новая baseline-схема с 12 полями users и отдельной таблицей roles; учётная запись создаётся bootstrap, не миграцией.
**Rationale**: Условия полноты списка заданы для неизменного набора. Сервис уже ориентирован на новую пустую базу, аккаунты схемы users_roles_20260927 сохраняются forward-миграцией. Старую рабочую базу автоматически не удалять и не stamp-ить.
**Alternatives considered**: Cursor pagination и snapshot всех страниц не нужны для заданной гарантии; миграция со встроенными секретами смешивает схему и эксплуатацию.

## 7. Проверки

**Decision**: Unit tests на доменные переходы и сценарии с fake-портами; HTTP contract tests; PostgreSQL tests двух сессий для гонок и индексов; отдельные startup tests с параллельными процессами. SQLite остаётся быстрым дополнительным режимом, не доказательством конкурентности.
**Rationale**: Существующие tests/integration/conftest.py поддерживают изолированные схемы PostgreSQL по UMS_TEST_POSTGRES_URL. Требуются проверки commit failure, stale sessions, двух ролей и защищённого статуса и запрета изменения superadmin.
**Alternatives considered**: Только mocks или SQLite не проверяют выбранные PostgreSQL гарантии.

Все вопросы дизайна разрешены; оставшиеся бизнес-допущения перечислены в spec.md и не скрыты за техническими решениями.
